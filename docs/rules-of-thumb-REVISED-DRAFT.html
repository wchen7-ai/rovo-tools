Rovo Credits: Rules of Thumb for Customer Conversations

A working reference for "how much will Rovo cost us in credits?" during TAS/CSA Rovo engagement — rules of thumb for credit vs. token usage, the rate card, agent-design guidance, governance, and FAQs.

Figures are directional planning estimates, not billing quotes. For pricing, always involve the CSM and AE. Contributions welcome.

I. The one-line answer

Credits ≠ Tokens. Most everyday usage is a flat 10 credits per request; what matters is monthly burn against the pooled allowance, not per-request cost. A short question and a long one cost the same in standard chat.[1]

Mental model: credits are a monthly prepaid wallet, not a taxi meter. Count actions, not words.

Credits are pooled org-wide, reset monthly, don't roll over.[1] Shortcut: credits ≈ AI actions × 10. A Premium app allowance of 70 ≈ 7 chat/agent requests/user/mo — individual allowances fill fast; the Teamwork Collection (10×) is the comfortable tier.

Technical-buyer nuance: TWG API calls run 1–10 cr each; writes are free (create a Jira issue), reads cost (summarize a page). Free all month: Search, summaries, definitions, chart insights.[1]

IV. Reading a customer's usage & forecasting

Active users — the number that drives the estimate. Define active users by actual Chat + Agent usage, not seats and not the headline AI MAU.[16]

New · how to read it from Customer 360 Open Cloud Usage → "Rovo capabilities: Monthly active users" and read the Chat users (plus Agent users) line. Average the last 3 months for a steadier basis — a single month can be noisy. Don't use Total AI MAU or Search users — those count free search and aren't credit-consuming users. Seats set the allowance; active users drive usage.

Forecast: (monthly interactions × credits per interaction) vs. pooled allowance. Rough workflow costs (these are batch/whole-job figures, not single actions): a triage rule over ~20 tickets ~200/run (20 × 10) · three bulk-import creates ~150 · one Confluence Create ~70 · a weekly Insights digest ~50. Per single action it's still the flat ~10 cr.[5]

AI Aha adoption anchor (internal): meaningful adoption ≈ 10 Rovo Chat messages (~100 cr)/user; product value across Jira + Confluence ≈ ~1.7k credits.[12]

A worked example — "will this org stay within budget?"

Illustrative only — round numbers, not a real customer.

Take a 100-seat Confluence Premium org. At 70 credits/user, that's 7,000 credits/month pooled across everyone.[1] Seats set the allowance; active users drive usage.

The usage bands (from the official Rovo Calculator's benchmark bands, converted at the flat 10 cr/request): Light ≈ 1 request/user/mo (~10 cr) · Moderate ≈ 2 (~20 cr) · Heavy ≈ 10 (~100 cr). Bands are built from active-customer usage; the ~175 cr aspirational high-water mark is Atlassian's own internal blended average.[12]

Today's reality — most orgs Real adoption is low — far fewer active users than seats, and credit utilization often in the low single digits. Say ~15 of 100 seats use Rovo in a month, mostly Light–Moderate (~1–2 requests) → ≈ 15 × ~15 cr = ~225 credits/month against 7,000, roughly ~3% of the pool. This matches the field: customers are barely touching their allowance pre-enforcement.

What changes the picture — heavier adoption + automation:

  • ~40 active users at the Moderate–Heavy end (~10 actions/mo, ~100 cr) → ≈ 4,000 credits/month interactive.
  • Add automation — a couple of agent-firing rules at ~30 runs/day org-wide ≈ 600 runs × 10 cr = ~6,000 credits/month.
  • Interactive (~4,000) + automation (~6,000) = ~10,000 vs. a 7,000 pool → over, driven mostly by automation, not the human users.
Takeaways to keep in your pocket Most orgs sit well under their pool today — utilization is low, the headroom is real. Pooling absorbs uneven human use — a room of Light users leaves headroom, so a few Heavy users (~175) is fine; no one is capped at their own 70. And automation is the swing factor, not per-user chat — one busy event rule can outweigh all the humans combined.

Model the specific customer in the Rovo Credit Estimator — plug in their real seats, editions, active users (3-month Chat+Agent MAU, not total AI MAU), activity mix, and automation runs for a proper per-driver breakdown and a green/amber/red verdict. The bands above are a "which bucket" gut-check, not a forecast.

V. How credit consumption shapes agent design

Default to a standard single agent on the flat 10-credit rate. Reach for a heavier reasoning mode (Think Deeper / Max) only when the task genuinely needs multi-step planning or cross-source judgement — a cheap wrong answer you re-run costs more than one good expensive one.

What the popular agents actually cost — three buckets

Looking at Atlassian's out-of-the-box agents,[4] credit consumption sorts into three design patterns. Which bucket an agent falls into matters far more than its per-run rate:

  • Flat-rate, human-triggered (most agents) — a person runs them interactively, single-step, flat 10 cr. The bulk of the catalog: Product Requirements Guide, Release Notes Drafter, Readiness Checker, Work Item Organizer, Bug Report Assistant, OKR Generator, Global Translator. Cost scales gently with adoption; easy to budget.
  • Agents wired into automation (the volume multiplier — watch these) — an agent connected to an automation rule so it runs automatically when the rule fires, with no human present. Credits then scale with how often the rule fires, not with headcount. The official catalog builds two agents specifically for this: Blocker Checker and Service Triage (both "designed for automations"). A triage rule on "every new ticket" can fire thousands of times a month — usually the single biggest credit driver in an org, dwarfing interactive use.
  • Cross-source judgement agents (use Think Deeper as a one-off) — agents whose job is to reason across multiple sources and make a judgement call: Rovo Ops, Jira Delivery Agent, Customer Insights, Transcript Insights Reporter. These are the genuine case for the heavier Think Deeper tier — but use it as a one-off for the specific hard task, not as the agent's default. A triage agent is the pattern in miniature: keep it on Quick Answers for rule-based routing (flat 10 cr), bump to Think Deeper only for the ambiguous tickets that need judgement, and reserve Max for open-ended cross-tool investigation once it ships.
Modelling note — automation ≠ Rovo credits Customer 360's automation-run count is the total automation across Jira/Confluence, not the subset wired to a Rovo agent. Only agent-connected runs spend credits. When you model automation in the Rovo Credit Estimator, enter only the Rovo-involved runs, not C360's total — otherwise you'll massively overstate burn.

Sub-agents don't double the cost — but separately-metered actions do add up. If you chat with a main agent (10 cr) and it hands off to a sub-agent for ordinary reasoning, you are not charged another 10 cr — the main agent and its sub-agents run as one invocation on one model, and their skills are billed collectively as a single ~10 cr interaction.[10]

The exception: if a sub-agent triggers an action that is separately metered, that action bills at its own rate on top of the 10 cr — each billable AI action is metered per event at its own rate-card rate.[1]

  • Sub-agent → fires an automation-connected agent run = +~10 cr per run.
  • Sub-agent → Confluence Create with Rovo = +~70 cr for the create.
  • Sub-agent → Think Deeper = that step bills at the variable Think Deeper rate.

Rule of thumb: one agent interaction is ~10 cr no matter how many sub-agents reason inside it, plus the rate of any distinct billable action (Create, Think Deeper, another agent run) invoked along the way.

For one-off heavy synthesis in Chat (not agents), Deep Research still exists — ~100 cr, up to 15 min, full citations.[10]

VI. Customer FAQ — definitions & gotchas

On Confluence, each Q&A below renders as a collapsible expand macro (question = title, answer = collapsed body); the two subsections that follow are also collapsible.

  • What counts as an "interaction"? One billable request. A 5-message chat = ~50 cr, regardless of length. Search/summaries free.[1]
  • How do we define an active user? Actual Chat + Agent users (3-month avg from the C360 MAU panel), not Total AI MAU (search-dominated). See §IV.
  • "I don't want surprise bills — what if we run out?" Extra usage is off by default — no automatic overage. In-flight work completes; only new requests pause, and free features keep working. Pool resets monthly. Admin alerts at 80% / 100%, hard cap available.[3]
  • "Does it cost more depending on where I use it — Slack, Teams, Jira?" No "app tax." Cost is set by the feature (Basic 10 cr vs. Premium variable), not the surface. What changes your pool is which subscriptions fund it — not where you spend.[3]
  • "Why should I pay for context / API calls?" 3P tools pulling Atlassian context via the Teamwork Graph API bill 1–10 cr/call. You're paying for permission-aware business context, not just model output.[14]
  • "Is everything moving to this model now?" No — some capabilities (e.g. Loom AI) stay on a separate system for now. Scope the specific products in play.

Which subscriptions fund credits?

Only four fund the pool — Teamwork Collection is a bundle, not a fifth app.[1]

  • Funds the pool: Jira, Confluence, JSM — 25/70/150; Teamwork Collection — 250/700/1,500 (≈10×).
  • Spends, no own allowance: Loom AI, JPD, Trello, Strategy Collection.
  • Free / graph-only: Analytics chart insights, Search, summaries, definitions; connectors feed the graph, cost only via TWG API.[14]

Sizing warning: the Teamwork Collection already includes Confluence, Trello, Atlas, Loom — count the Collection or the apps, never both.

Which products spend credits — grouped by maturity

Confirmed (GA):

  • Core apps (Jira/Confluence/JSM): Chat, Agents at standard rates; Search/summaries free.[1]
  • Loom: AI features spend ~70–300/run.
  • Strategy Collection: own AI; spends from the pool at standard rates, no own allowance.[17][18]

Verify — limited or unconfirmed:

  • JPD: gaps (ideas flat text, Insights not indexed); chat/agents at standard rates.
  • Trello: outside the standard model — verify with account team.
  • Analytics: native chart insights free today (Verify). But Rovo cross-product reporting (sprint data → Confluence) is a Rovo action, ~10 cr — chart insights free; generating the report is not. ("Rovo for analytics" is ambiguous — clarify native Analytics AI vs. Rovo reporting; entitlement differs.)

VII. Admin controls & governing usage

No single "usage cap" toggle. Governance splits into two things: who controls what (admin architecture) and how you keep consumption in check (usage governance).[11]

A. The admin architecture — three layers, top-down

Control flows from the org down to a single agent. Each layer has a different owner and a different job:

  1. Org admin — turns Rovo on and sets the boundary. Enable/block Rovo per app, set rollout scope (pilot groups → org-wide), IP allowlists, connectors, usage visibility. MCP lives here too — enable/disable the MCP server, allowed domains, and read/write/search permission groups (org-wide today, not per-site).
  2. Studio admin — governs what gets built. The builder control plane: assign OOTB agents, create custom agents, build apps (App Builder), build automations, and attach agents to knowledge sources (connectors). Three independent creator roles gate this — agent, app, automation — grantable by user or group.
  3. Agent owner / manager — governs a single agent. Who can use and edit it, what skills/tools it can call, and its instructions. Owners can make an agent private or share it with named users.

B. Governing usage — where to watch, alert & cap

  • Review usage — Admin → Rovo → Insights: total usage over time, by app, by user. Where a heavy-user hotspot or runaway automation shows up.[5]
  • Set alerts & caps — 80% / 100% notifications; extra-usage caps are opt-in and off by default, so no accidental overage.[3]
  • Restrict who can build — the single biggest burn lever. Limiting agent (especially automation) creation prevents "builder sprawl," the usual cause of runaway growth.

Recommended stack (best practice):[20]

  • Access shape — broad Rovo usage, narrow Studio access, restricted creators.
  • Phase the rollout — pilot group first, keep early agents private, then expand in waves.
  • Showback before chargeback — make usage visible to stakeholders first, then decide whether formal cost allocation is needed.

Governance gaps to flag — four controls admins expect but don't fully have yet:[11]

  • No per-agent group sharing. You can restrict who sees an agent, but only by naming individual users — there's no "share with this team/group." Managing a sensitive agent across a large team means adding people one by one. (Group support is in progress.)
  • No hide-until-approved workflow. An agent a non-admin builds can't be held hidden pending formal admin sign-off. The workaround is a sandbox: build and test there, then move approved agents to production. Admin "verification" is a trust badge, not a gate.
  • MCP controls are org-wide, not site-scoped. Enabling/disabling the MCP server, allowed domains, and permission groups apply to the whole org — you can't tune MCP for one site or business unit independently.
  • Usage forecasting is still "coming soon." Admins get 80% / 100% threshold alerts, but the forward-looking spend forecast in Insights isn't live yet — no projected end-of-cycle burn inside the product.

Two ways an agent can now be invoked programmatically — both admin-gated.

Changed · Rovo Public Agents API A documented REST API (/gateway/api/rovo/v1) to open a conversation with an agent by ID and send messages, via OAuth 2.0. EAP + allowlisted — not yet GA self-serve; confirm the org is enabled before promising it.[19]
Changed · Agent2Agent (A2A) A live, customer-documented protocol letting compatible 3P agents (e.g. Claude, Gemini) and custom agents connect to Rovo and act across Jira/Confluence using the user's existing permissions. OAuth 2.1; the org admin must enable A2A in Admin Hub first — a governance lever, not a bypass.[6][7]

Credit treatment is settled either way: an agent call triggered through either path spends credits like any other invocation.[1]

VIII. Honest caveats

  • No universal rule of thumb for exact per-prompt cost — variable-mode depends on prompt, model, use case.
  • Rate-card values beyond the official Support page are directional; may change before enforcement (~Dec 2026).
  • Usage profiles are directional "which bucket" anchors, not a per-customer forecast — model the specific customer in the Estimator.
  • "Free" = 0 credits today. May change once enforcement begins (~Dec 2026) — re-check the current rate before quoting.
